3. Build the Claude prompt based on intent:
   - System prompt: "You are a calm, direct rowing coach. Keep responses under 2 sentences for mid-session intents, up to 4 sentences for debrief. Reference the athlete's current metrics when relevant. No filler phrases. Tone: supportive but honest. Never use 'Great job!' as a standalone response."

   - For `push_me`: include current metrics, ask Claude to encourage pushing harder with a specific target. Max tokens: 60.
   - For `im_good`: include current metrics, ask Claude to briefly acknowledge. Max tokens: 40.
   - For `debrief`: include full sessionSummary, ask Claude to recap 3-4 key stats and call out one standout moment (per D-14). ADDITIONALLY, instruct Claude to end the response with a fenced JSON block containing coach memory entries: `\n\n---COACH_MEMORY---\n[{"key":"...","value":"..."},...]`. The prompt must say: "After your spoken debrief, output the separator ---COACH_MEMORY--- on its own line followed by a JSON array of {key, value} objects representing things to remember about this athlete for future sessions (e.g., preferred_rate, endurance_trend, injury_notes). 4. Call `client.messages.stream()` with model `'claude-haiku-4-5'` (verify model string against Anthropic docs).

5. Stream response back as SSE: for each `content_block_delta` with `text_delta`, encode as `data: {"text":"..."}\n\n`. Send `data: [DONE]\n\n` at end. Set headers: Content-Type text/event-stream, Cache-Control no-cache.

6. Read `ANTHROPIC_API_KEY` from `process.env.ANTHROPIC_API_KEY`. If missing, return 500 with `{"error":"ANTHROPIC_API_KEY not configured"}`.

Create `src/app/api/tts/route.ts` as an Edge runtime route handler. This route proxies text to Cartesia Sonic-3 TTS and streams audio chunks back. The POST handler must:

1. Parse request JSON: `{ text: string, voiceId?: string }`
2. Validate `text` is non-empty, max 500 characters. Return 400 if invalid.
3. Read `CARTESIA_API_KEY` from env. Return 500 if missing.
4. Read `CARTESIA_VOICE_ID` from env (default voice). Use request `voiceId` if provided.
5. Call Cartesia TTS API. Use the SSE/HTTP streaming endpoint (NOT WebSocket, since this is a stateless route handler):
   - URL: `https://api.cartesia.ai/tts/sse`
   - Method: POST
   - Headers: `X-API-Key: {key}`, `Cartesia-Version: 2025-04-16`, `Content-Type: application/json`
   - Body: `{ model_id: "sonic-3", transcript: text, voice: { mode: "id", id: voiceId }, output_format: { container: "raw", encoding: "pcm_s16le", sample_rate: 24000 } }`
6. Stream the Cartesia SSE response directly back to the client. Each Cartesia SSE event is `data: {"data":"<base64-pcm>","done":false}` or `data: {"done":true}`. Forward these as-is.
7. Set response headers: Content-Type text/event-stream, Cache-Control no-cache.

Note: The pre-computed cue path (COACH-02 <500ms) uses the client-side Cartesia WebSocket directly via NEXT_PUBLIC_CARTESIA_API_KEY. This TTS route is for the LLM path (check-in greeting, mid-session responses, debrief) where text is generated server-side and latency tolerance is higher.

Create `src/lib/coaching/session-writer.ts` with two exported functions:

1. `writeSession(data: SessionWritePayload): Promise<{ id: string } | null>` — inserts a row into the `sessions` table via Supabase client. Maps payload fields to table columns:
   - `user_id: data.userId`
   - `started_at: new Date(data.startedAt).toISOString()`
   - `ended_at: new Date(data.endedAt).toISOString()`
   - `duration_s: Math.round((data.endedAt - data.startedAt) / 1000)`
   - `total_meters: data.totalMeters`
   - `avg_split_ms: data.avgSplitMs`
   - `avg_watts: data.avgWatts`
   - `avg_stroke_rate: data.avgStrokeRate`
   - `energy_level: data.energyLevel`
   - `session_type: data.sessionType`
   Returns the inserted row's `id` or null on error. Log errors to console but do NOT throw — writes are fire-and-forget (per ARCHITECTURE.md Pattern 3: Write-Behind).

2. `writeCoachMemory(userId: string, entries: CoachMemoryEntry[]): Promise<void>` — upserts each entry into `coach_memory` table using `.upsert()` with `onConflict: 'user_id,key'`. This ensures each key is a single row per user (per RESEARCH.md Pitfall 6 prevention). Log errors but do not throw.

Both functions import `createClient` from `@/lib/supabase/client`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> /api/coach | Untrusted intent + sessionContext from client |
| Client -> /api/tts | Untrusted text from client for TTS synthesis |
| /api/coach -> Anthropic API | API key stored server-side |
| /api/tts -> Cartesia API | API key stored server-side |
| session-writer -> Supabase | Auth context from client cookie |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06 | Tampering | /api/coach route | mitigate | Validate intent is one of 5 allowed values; reject with 400 otherwise. sessionContext is used only for prompt construction (no SQL injection vector). |
| T-02-07 | Denial of Service | /api/tts route | mitigate | Validate text length <= 500 chars to prevent abuse of TTS API quota. Rate limiting deferred to Vercel/Cartesia account limits. |
| T-02-08 | Information Disclosure | /api/coach route | mitigate | ANTHROPIC_API_KEY in server-side env only (not NEXT_PUBLIC). Edge runtime ensures key never reaches client bundle. |
| T-02-09 | Information Disclosure | /api/tts route | mitigate | CARTESIA_API_KEY in server-side env only for this route. Client-side key (NEXT_PUBLIC_CARTESIA_API_KEY) is separate and rate-limited. |
| T-02-10 | Spoofing | session-writer | mitigate | Supabase RLS enforces auth.uid() = user_id. Client cannot write sessions for other users even if they tamper with the userId field in the payload. |
</threat_model>
